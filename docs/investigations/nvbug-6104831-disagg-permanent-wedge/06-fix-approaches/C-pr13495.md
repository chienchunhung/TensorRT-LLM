# Approach C — PR `#13495` Plus Sig `#4`, Eval-Order, and Idempotency

PR [#13495](https://github.com/NVIDIA/TensorRT-LLM/pull/13495) layers on
top of PR [#13439](https://github.com/NVIDIA/TensorRT-LLM/pull/13439)
(the conservative request-lifetime hardening). It adds NIXL
transfer-release cancellation logic at the backend boundary plus a
bundled 512-line design doc. Approach C combines that with three local
patches to close the layers PR `#13495` doesn't address.

---

## What it contains

### PR `#13439` (the base of `#13495`) — conservative lifetime hardening

- C++ generation receive tracking keeps `std::shared_ptr<LlmRequest>`
  while the async receive future is outstanding (closes L2 receive side).
- Receiver worker queues keep `std::shared_ptr<LlmRequest>` while
  queued or executing (closes L2 receiver-queue side).
- Python global error handling fails closed when generation KV receive
  is still in flight, instead of freeing request resources under raw
  C++ users. (Different philosophy from `#13056`'s "remove guards
  because shared_ptr makes them safe.")
- Python termination avoids freeing resources while context transfer
  is still in progress.
- `BufferIndexHolder` for buffer-index slots. Adds a `TransferSession`
  type that owns AgentConnection pre-assigned recv buffer-index from
  pre-assignment through formatter `unformat()`. (Closes L5 with a
  step toward the unifying abstraction the architectural reflections
  call for.)
- C++ worker/future paths gain catch-all handling for unknown
  exceptions; non-`std` throws become promise/future errors.

### PR `#13495` — additions on top of `#13439`

- **`TransferStatus::release()`** added to the C++ transfer-status
  interface.
- **`NixlTransferStatus::release()`** implemented as
  `nixlAgent::releaseXferReq()`. Destructor releases outstanding
  handles as a final cleanup guard. **Closes L6 — this is the unique
  contribution of `#13495` that no other approach has.**
- Sender-side transfer wait now polls in bounded intervals, observes
  `DataContext::getTransferTerminate()`, and calls `status->release()`
  before surfacing cancellation.
- Sync and ready notification waits return whether the expected
  notification actually arrived. Receive paths fail when termination
  stops a notification wait instead of treating that as a successful
  receive.
- `release()` exposed through nanobind to Python.
- **Sender cancellation completes the moved-out promise with an
  explicit `RequestSpecificException`** after sender bookkeeping has
  been erased. This is a different ordering from `#13640`'s pre-erase
  fulfillment — empirically tested under stress, intended to avoid a v2
  regression where future-ready-too-early caused races.

### Local patches on top of `#13495`

- **Sig `#4` non-blocking future fix** (closes L4). `#13495` does not
  carry this. `#13671`'s `wait_for(0)` skip is **strictly required**
  for any landing path that includes `#13495`.
- **Eval-order fix in `CacheSender::Impl::handleAsyncSend`** (closes L7).
  Required because `#13439` also makes `Response::mRequest` a
  `shared_ptr`, triggering the same argument-evaluation-order hazard.
- **Python idempotency guards** (closes L8). Same as approach B.

## What it covers (`L1`–`L8`)

| Layer | Coverage | Mechanism |
|---|---|---|
| **L1** sig `#1` | ✓ | explicit `RequestSpecificException` on the moved-out promise (post-erase ordering) |
| **L1** sig `#5` | ✗ | `#13495` doesn't address the queued-cancel erase path; description acknowledges *"`Cannot cancel request` may still appear"* |
| **L2** request lifetime / UAF | ✓ | inherited from `#13439` |
| **L3** in-process cancellation primitive | ✗ | relies on existing `DataContext::transferTerminate` only; no per-request cancel-flag registry |
| **L4** `checkGenTransferStatus` blocking | ✓ | local sig `#4` fix is required |
| **L5** recv-buffer slot leak | ✓ | inherited from `#13439` (`BufferIndexHolder` + `TransferSession`) |
| **L6** NIXL backend handle release | ✓ | **only `#13495` has this**: `TransferStatus::release()` → `nixlAgent::releaseXferReq()` |
| **L7** eval-order regression | ✓ | local eval-order fix |
| **L8** Python scheduler idempotency | ✓ | local idempotency guards |

## What it leaves uncovered

**L3 and L5-sig-`#5`** are the structural gaps:

- L3 (in-process cancellation primitive) — `cancelRequest` returns
  false on in-flight, log noise accumulates, wedged transfers pile up
  under contention.
- L1 sig `#5` (receiver queued-cancel erase) — `cancelRequest` erases
  queued entries without fulfilling promises, producing
  `Broken promise` on the receiver side.

Without L3 specifically, the deadlock variant of sig `#7` becomes more
likely than it would be in approach D, because the cancel-flag flow
that breaks `CacheSender::Impl::response()` out of its `mCondMutex`
cv-wait doesn't exist.

## Empirical result

After applying `#13495` + local patches, the user-side stress harness
behaves as follows:

- The ctx Python-`getattr` SIGSEGV (sig `#7` Variant C) and the
  `emplaceDone` assertion no longer reproduce — both addressed
  incidentally by the L7 + L8 patches.
- The direct-UCX stress harness still ends in **no-recovery**, with
  the gen event loop later failing on a stale-sequence issue
  (`unordered_map::at` from `KVCacheManager::addToken`).

The residual no-recovery is consistent with L3 being open: even though
L6 closes the NIXL handle stranding, the in-process cancel primitive
that would unblock `CacheSender::Impl::response()` from its
`mCondMutex` cv-wait isn't there. Under sustained contention the wedge
still forms.

The stale-sequence `unordered_map::at` failure is consistent with the
half-closed L1 (sig `#5`): cancelled queued requests still leave gen-
side state in an inconsistent shape that surfaces later in the gen
event loop.

## When to use this approach

- **For `rc11` backport** — a defensible standalone choice if
  `#13056`'s broader refactor is too invasive for the release branch.
  The conservative Python policy ("fail closed without freeing") is
  operationally safer because the customer's K8s/Dynamo deployment
  recovers via pod restart anyway.
- **For `main`** — strictly weaker than approach D. The L3 gap means
  the customer's stress harness still wedges; landing `#13495` alone
  on `main` would require an additional follow-up to add the
  per-request cancel-flag primitive.

---

## Strengths

- **`releaseXferReq()` at the backend boundary** is the genuinely novel
  contribution that no other approach has. Even after the deadlock in
  `CacheSender::Impl` is fully fixed, this primitive belongs in the
  codebase because it tells NIXL when to drop a transfer handle on
  cancel.
- **`TransferSession` type** is one step closer to the unifying
  abstraction the architectural reflections advocate as a long-term
  goal.
- **Bundled 512-line design doc** (`docs/source/developer-guide/disagg-kv-transfer-hardening-plan.md`)
  makes the rationale and the decisions explicitly reviewable.
- **More conservative than `#13056`**: smaller blast radius per change,
  keeps the defensive Python guards.
- **Empirically tested ordering for the cancel-after-ready
  set_exception path** — `#13495`'s post-erase ordering is the version
  that survived a v2 regression under stress.

## Weaknesses

- **Doesn't close L4** — sig `#4`'s `checkGenTransferStatus` blocking
  is unaddressed. Without local patches, the gen event loop self-blocks
  on the first stuck transfer.
- **Doesn't close L3** — no per-request cancel-flag primitive. The
  `Cannot cancel request` log line persists; the deadlock variant of
  sig `#7` remains likely.
- **Doesn't close L1 sig `#5`** — receiver queued-cancel erase path
  unchanged. `Broken promise` can still fire on the receiver side.
