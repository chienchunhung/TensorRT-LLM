# Approach B — PR `#13056` Plus Eval-Order and Idempotency

The broad architectural lifetime / cancellation refactor in PR
[#13056](https://github.com/NVIDIA/TensorRT-LLM/pull/13056), with two
small local patches added on top to close the regressions and
scheduler-side gaps that PR `#13056` exposes but doesn't address.

---

## What it contains

### PR `#13056` — 16 commits, summary

The largest single behavioural change is moving the transceiver toward
end-to-end request ownership and a more systematic cancellation model:

| Commit (or commit range) | What it does |
|---|---|
| `649d1466bb7a` | `Response::mRequest` and `RequestAndPromise::mRequest` change from raw `LlmRequest*` to `std::shared_ptr<LlmRequest>`. `mSenderFutures` and `mRequesterFutures` likewise. Closes the L2 UAF surface. |
| `7e8016a2fa44` / `e7fcbab015f2` / `62c5d24ae68f` | New per-request cancel-flag registry on both `CacheSender::Impl` and `CacheReceiver::Impl` (`mInFlightCancelMutex` + `mInFlightCancelFlags`), plumbed through `sendRequestInfo`, `receiveReadySignal`, and `AgentConnection::send`'s polling loop. Closes L3. |
| `a3197756488d` / `a8c27a45bb5d` / `3d0a6d183cdd` | `kv_transfer_timeout_ms` enforcement plus deadline-hoist above the readiness gate. Partial L4 closure (eviction at deadline, not non-blocking poll). |
| `2860ac50a54e` / `39f5452ea5f3` / `28f836e190fd` / `6f85ce895b41` | RAII `BufferIndexHolder` for both receiver and sender formatters; bounded `wait_for(slice_ms)` loops in `assignBufferIndex`. Closes L5. |
| `abfcb6d39777` | `catch(...)` on the receiver drain worker loop. Closes a related but distinct invariant (worker-loop hardening; not in L1–L8 framing). |
| Various Python-side commits | Removes Path A/B guards in `py_executor.py`'s `_handle_responses` and `_check_disagg_ctx_cache_transfer_status` because L2's `shared_ptr` makes them unnecessary. |

### Local patches on top of `#13056`

- **Eval-order fix in `CacheSender::Impl::handleAsyncSend`** (closes L7).
  Materializes `reqId` before `std::move(resp)`:
  ```cpp
  TLLM_CHECK(resp.mRequest != nullptr);
  auto const reqId = resp.mRequest->mRequestId;
  sendAndRemoveResponse(reqId, std::move(resp));
  ```
  Required because `#13056`'s L2 fix changes `Response::mRequest` from a
  raw pointer to `shared_ptr`, which makes the previous form
  argument-evaluation-order-unsafe.
- **Python idempotency guards** (closes L8) in `_prepare_disagg_gen_init`
  and `_recv_disagg_gen_cache`:
  - `_disagg_gen_init_prepared_ids`, keyed per `ResourceManagerType`,
    so each resource manager prepares a given `py_request_id` at most
    once.
  - `_disagg_gen_kv_recv_started_ids`, so the receive side is only
    started once for a given `py_request_id`. The synchronous path
    discards the id on exception so a real failed start can still be
    retried.

## What it covers (`L1`–`L8`)

| Layer | Coverage | Mechanism |
|---|---|---|
| **L1** sig `#1` | partial | per-request cancel-flag flips on cancel; worker observes flag and throws → `catch(std::exception)` calls `set_exception(current_exception())`. The specific `mReadyResponses` cancel-after-ready erase site in `sendResponse`'s "else" branch is unchanged. |
| **L1** sig `#5` | partial | cancel-flag covers the in-flight path; the in-queue erase path is unchanged. |
| **L2** request lifetime / UAF | ✓ | `shared_ptr<LlmRequest>` through transceiver |
| **L3** in-process cancellation primitive | ✓ | per-request cancel-flag registry |
| **L4** `checkGenTransferStatus` blocking | partial | `kv_transfer_timeout_ms` deadline-hoist evicts after timeout but still blocks for the deadline duration on the first stuck future per poll |
| **L5** recv-buffer slot leak | ✓ | `BufferIndexHolder` (receiver + sender formatters) |
| **L6** NIXL backend handle release | ✗ | not addressed |
| **L7** eval-order regression | ✓ | local eval-order fix |
| **L8** Python scheduler idempotency | ✓ | local idempotency guards |

## What it leaves uncovered

**L6 (NIXL backend handle release on cancel)** is the structural gap.
PR `#13056` has bounded waits and per-request cancel-flags but never
reaches into the backend transfer-status interface. Cancelled
mid-transfer requests leave NIXL `XferReq` handles registered until
the underlying transfer completes naturally or the worker shuts down.
Under contention, accumulated handles correlate with the deadlock
variant of sig `#7`.

The L1 partial coverage (sig `#1` and `#5`) is also worth being
explicit about: the worker's `catch(std::exception)` calls
`set_exception` on the existing promise, but only because the
cancel-flag flow throws an exception that propagates out. The cleaner
approach is to fulfil the promise *at the erase site itself* with a
structured `RequestSpecificException` (the `#13640` / `#13495` pattern).
The L1 cleanup in `#13056` is functionally adequate but not
idiomatic.

## Empirical result

After applying `#13056` and the two local patches, the user-side stress
harness behaves as follows:

- The deterministic first-request `handleAsyncSend` SIGSEGV (sig `#7`
  Variant D) is removed by the eval-order fix.
- The `emplaceDone` assertion that surfaces post-eval-order is removed
  by the Python idempotency guards.
- Some direct-UCX runs recovered, including a `CONC=24` run.
- However, recovery was **not yet consistently clean across repeats**.
  Earlier repeats showed no-recovery / backlog patterns under sustained
  contention.

The recovery inconsistency is consistent with L6 still being open: when
a cancel-during-transfer event leaves a NIXL/UCX handle stranded, the
sender's `response()` worker can deadlock on the next contention-driven
mutex acquisition.

## When to use this approach

- **As a `main` integration step** — yes, this is the right
  architectural foundation. PR `#13056`'s L2 (`shared_ptr`) and L3
  (cancel-flag) closures are load-bearing for everything else.
- **As the sole fix for the customer's NIXL deployment** — no. L6
  uncovered means stranded NIXL handles accumulate. Pair with
  `#13495`'s `releaseXferReq()` mechanism (i.e. land approach D).

---

## Strengths

- Architectural correctness: `shared_ptr<LlmRequest>` closes the UAF at
  the source rather than working around it with Python-side guards.
- Per-request cancel-flag is a *reusable* primitive that retires the
  `Cannot cancel request` log noise structurally.
- 16 commits with detailed messages and explicit empirical evidence
  (~15 saturation iterations during development).

## Weaknesses

- Larger blast radius (16 commits, multiple file groups, removes
  defensive Python guards on the bet that `shared_ptr` perfectly closes
  every UAF).
- L6 gap means the customer's NIXL transport still has the handle-
  stranding failure mode under contention.
- Partial L1 coverage means cancel-after-ready promises are still
  fulfilled via exception propagation rather than at the erase site —
  more complex review surface.
- No bundled design doc; rationale lives in commit messages.
